# 16. 세그멘테이션
> 베이스와 바운드 방식은 유연성이 없다. 대형 주소 공간을 어떻게 지원할 것인가?

## 16.1 세그멘테이션: base/bound의 일반화
- MMU에 하나의 베이스/바운드 값이 존재하는 것이 아닌, **segment마다 베이스/바운드 값이 존재**
- 세그멘트(segment): 특정 길이를 가지는 연속적인 주소 공간 - 코드, 스택, 힙 세 종류
- 각 세그멘트를 물리 메모리의 각기 다른 위치에 배치 가능: 사용되지 않는 가상 주소 공간이 물리 메모리 차지하는 것 방지
- 세그멘트ㅡ별로 base/bound 값 저장 - 끝을 벗어난 공간을 접근하려고 한다면 segment fault 발생

## 16.2 세그멘트 종류의 파악
> 하드웨어는 가상 주소가 어느 세그멘트를 참조하는지, 그리고 그 안에서 오프셋은 얼마인지를 어떻게 알 수 있는가?
- 최상위 2비트를 세그먼트 종류를 나타내는 데 사용(base 파악 가능), 나머지 비트는 오프셋으로 사용
  - 일부 시스템은 코드와 힙을 하나의 세그먼트에 사용하고 종류를 나타내는 데 1비트만 사용
  - 최대 공간 크기(bound)를 증가시킬 수 없기 때문에 가상 공간 활용도가 떨어진다는 단점
- 하드웨어적 접근: 묵시적 접근 방식 - 주소가 어떻게 형성되었나를 관찰(프로그램 카운터로부터 생성되었는지, 스택/베이스 포인터에 기반을 두는지 등등)

## 16.3 스택
- 코드나 힙과는 달리 **반대 방향**(낮은 주소 방향)으로 확장되기 때문에 다른 방식의 변환이 필요하다.
- 세그멘트가 어느 쪽으로 확장되는지 파악해야 함: 순방향/역방향 정보 저장해야 함

## 16.4 공유 지원
- 주소 공간에 특정 메모리 세그먼트를 공유하는 방식으로 효율화: **코드 공유**가 일반적
- protection bit 추가 필요
  - 세그멘트를 읽거나 쓸 수 있는지/코드를 실행시킬 수 있는지
  - 하드웨어는 가상 주소가 범위 내에 있는지 확인 + 특정 액세스가 혀용되는지까지 확인해야 함

## 16.5 소단위(fine-grained) 대 대단위(coarse-grained) 세그멘테이션
- 대단위 세그멘테이션: 코드, 스택, 힙
- 소단위 세그멘테이션: 주소 공간을 작은 크기의 공간으로 잘게 나누는 것
  - 많은 수의 세그멘트 지원 -> 여러 세그멘트 정보를 저장하기 위한 세그멘트 테이블 필요

## 16.6 운영체제의 지원
> 시스템은 각 주소 공간(세그멘트) 단위로 가상 주소 공간을 물리 메모리에 재배치하기 때문에, 하나의 베이스-바운드 값을 갖는 것에 비해 물리 메모리를 절약할 수 있다. 세그멘테이션 도입을 위해 운영체제는 어떤 문제를 해결해야 할까?
1. context switch
- 운영체제는 세그멘트 레지스터의 저장과 복원을 실행해야 함: 각 프로세스는 자신의 가상 주소 공간을 가짐
2. 세그멘트 크기 변경
- 객체를 할당할 때, 빈 공간을 찾고 기존 힙에서 해당 요청을 처리할 수 있도록 처리
- 빈 공간이 없다면 힙 세그먼트 크기 증가
- 시스템에 존재하는 메모리가 고갈되었거나, 이미 프로그램이 과도하게 많은 메모리를 사용하고 있을 경우, 메모리 할당 요청 거절 가능
3. 미사용 중인 물리 메모리 공간의 관리
- 새로운 주소 공간이 생성되면 세그멘트를 위한 비어있는 물리 메모리 영역을 찾을 수 있어야 함
- 프로세스는 많은 세그멘트를 가질 수 있으며, 각 세그멘트는 크기가 다를 수 있음
- 외부 단편화(external fragmentation): 물리 메모리가 빠르게 작은 크기의 빈 공간들로 채워지는 것
  - 기존 세그멘트를 정리하여 물리 메모리를 압축: 빈 공간 확보 -> 세그멘트 복사는 메모리 부하가 크고 시간을 많이 소모하기 때문에 압축은 비용이 많이 듦
  - 빈 공간 리스트를 관리하는 알고리즘 사용: best-fit, worst-fit, first-fit / 버디 알고리즘 등
  - 외부 단편화를 가능한 줄이는 것이 목표
